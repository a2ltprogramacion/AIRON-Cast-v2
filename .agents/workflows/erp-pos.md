# Workflow: erp-pos
## Objetivo
El core central de máxima complejidad del entorno AIRON-Cast. Diseñado obligatoriamente para la confección y escalamiento de Módulos ERP-POS Core de alta envergadura tecnológica (usualmente apalancados sobre bases corporativas tipo Django 5 + PostgreSQL 16 + Astro 4 orientados a SMBs en el exigente ecosistema operativo venezolano).

## Agentes y orden de ejecución
`strategist` → `backend` → `frontend` → `ux` → `qa` → `docs`

## Paso a paso del flujo
1. El analista vitalicia la primera instancia forjando el master blueprint dictaminando microservicios o apps acoplables de Django en `spec.md`. Define tareas masivas iterativas por cada agente. 
2. Mueve control hacia `backend`, quien implementa la arquitectura relacional (modelos complejos, lógica P.O.S de transacciones financieras consistentes). Ejecuta e incrusta migraciones exactas con sus checkpoints usando memoria y consultando `context7`.
3. Prosigue el ciclo turnado la visión orquestada al estrato cliente recayendo sobre `frontend` quien estructurará Astro / JS para conectar fluidamente las API creadas acoplando plantillas o diseños `StitchMCP` de meditarse necesario, forzando un código limpio transaccional.
4. El rol `ux` somete al escrutinio los flujos operativos generados por Frontend dictaminando reportes rigurosos dado el carácter delicado del ERP u caja de Punto de Venta.
5. El escaneo global por el taskforce de calidad `qa` valida meticulosamente tests de seguridad y cruce formal cliente-servidor, verificando todo checksum sin saltos ciegos.
6. Agrupa al final de la iteración completada el ensamble el agente `docs`, estructurando `docs/frontend.md`, `docs/backend.md`, y de un peso inconmensurable el `README.md` general maestro con instrucciones de instalación de infra.

## Criterios de completado
Se han compilado exitosamente las ramificaciones del proyecto, las migraciones reflejan el schema ideal. APIs rest blindadas de filtraciones en texto. Transaccionalidad garantizada entre endpoints sin caídas sintácticas. Un informe UX aprobado y firmado sumado al OK inmaculado emitido por QA. Exito documental.

## Artefactos esperados en output/
- Repositorio íntegro en `src/` abarcando la app server (Django), sus migraciones de BD puras y el cliente (Astro).
- Pliegos íntegros de variables en esquemas dummy `.env.example` y la batería global documental compilando exhaustivos manuales y especificaciones técnicas profundas en la capeta `docs/`.

## Condiciones de pausa / HITL
- Escala inexorablemente si la propuesta interfiere, rediseña o corrompe radicalmente la integridad referencial de los esquemas financieros o contables preestablecidos por Argenis.
- Emplear STOP_LOSS sobre transacciones en base de datos erróneas que resulten un peligro crítico y escapen a tres retrabajos iterados de código backend.
